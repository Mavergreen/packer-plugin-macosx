This release fixes a firmware cause of Mavericks guests not coming back
from a restart. Before, a restart
from inside the guest (`sudo reboot`, `sudo shutdown -r now`, or a
build's own restart) sometimes never came back: in our measurements,
between one restart in ten and one in twenty-five. The screen stayed
blank and SSH never answered. Stopping QEMU and starting it again always
worked, so `vagrant halt` and `vagrant up`, and `vagrant reload`, which
does both, were never affected.

The cause was the guest's firmware. On every boot it reads one page of
memory for settings that a confidential-computing loader would leave
there. This project never uses such a loader. Nothing stopped Mac OS X
from using that page as ordinary memory, and a restart does not clear
memory. So the firmware sometimes took leftover bytes for the number of
CPUs, then waited over an hour for CPUs that do not exist.

The firmware now does two things:
- It keeps that page to itself. This is upstream EDK II's own fix, which
  the OpenCore build tree this project pins had not picked up yet.
- It never reads the page at all. Snow Leopard writes over the page
  however the firmware marks it, so keeping it is not enough there.

A Snow Leopard build once hung at the restart after the 10.6.8 update:
the build waited for SSH until it gave up, with the guest's last words,
`MACH Reboot`, still on the screen. That one hang was most likely the
same one, and this change removes that cause (`docs/decisions/0030`).

`docs/decisions/0018` has the measurements.

A restart no longer stalls for most of a minute once in every sixty or so.
The firmware rewrites its console settings on every boot, and the old
copies pile up in its small settings store, which lasts until QEMU
exits. At about the 61st restart in one QEMU process the store is
nearly full, and the firmware compacts it before it starts Mac OS X.
Under QEMU that took 41 to 57 seconds, because QEMU writes the store's
file once for every byte, and on a busy host more than five minutes,
with only the TianoCore logo on the screen. The firmware now writes only
the bytes that change, and the same compaction takes seconds, not a
minute. `vagrant halt` and `vagrant up` start a fresh store, so only
guests restarted many times from inside were affected.
`docs/decisions/0032` has the measurements.

Boxes also shut down and restart without a 20-second stall, and without
keeping a report of one. A shutdown from inside a 10.9 guest could wait
20 seconds for a background process that would not quit, and 10.9 then
files a `.shutdownStall` diagnostic report. Every box carried three of
them, from the build's own restart and shutdowns. There were two causes:
- A login-window helper, `ManagedClient`, held the disk-arbitration
  daemon open. This hit every shutdown more than about 30 seconds after
  boot.
- The system's event agent, `UserEventAgent`, records each scheduled
  task it runs, and for a few seconds after that it has a record to save.
  It saves it when asked to quit, but a shutdown first stops the process
  that saves it, so the agent cannot quit until it is killed. This hit
  shutdowns soon after a boot, as the build's and the boot gate's are:
  10 of 40 in our measurements spread over the first two minutes, and 25
  of 60 at the boot gate's pace, even with `ManagedClient` stopped.

Boxes now carry `/usr/local/sbin/guest-macosx-shutdown`. It stops the event agent
while the process that saves its record still runs, so the record is
saved; it stops `ManagedClient`; and then it shuts down. The build, the
boot gate and `vagrant halt` all use it. With it, the event agent held
none of 160 shutdowns and restarts, and a restart takes about 20
seconds, not 40 (a restart soon after a boot, as `vagrant reload` right
after `vagrant up` is, takes up to about 30 seconds longer for the helper's
wait for jobs still starting).

Background processes still starting up held shutdowns too, in a boot's
first seconds: launchd asks every process to quit at once, and one that
has only just started can miss the request, or wait for a service the
shutdown has already stopped. That held 15 of 100 restarts made as soon
as a warm boot answered SSH, and the Apple ID agent, `AppleIDAuthAgent`,
held every first restart of a cold boot of the base box (8 of 8), while it
saved its account record. `guest-macosx-shutdown` now first waits until nothing
launchd started is under 20 seconds old. With it, none of 100 such
restarts stalled, and none of 8 first restarts of a base-box cold boot:
that is the 20 seconds, which carries the agent past its record. It also
waits out that agent's record as it does the event agent's; that wait did
not trigger in any of the 266 shutdowns we measured. It has logged once in
a real guest, for 1.3 seconds, in a restart right after we stepped the
guest's clock backward on purpose (a test artifact; we did not measure
whether that restart would have stalled without it). It is there for the
same check running later in a long-lived guest, which we have not
measured. A restart soon after a boot now waits up to about 30 seconds
for this, and says in `system.log` what it waited for, or that there was
nothing to wait for. `docs/decisions/0021` has
the mechanism and the measurements.

A separate startup race could kill `netbiosd` with HUP before it installed
its own signal handling, then delay its restart. On the measured 10.9.5
binary and original socket job, a small exec wrapper now initializes ignored
HUP first. The native late handler, socket ownership and SMB preference
publication remain intact; unknown configurations are left alone and logged.
`docs/decisions/0037` records the early-signal and name-reloading checks.

Known native limitation: the separate system `ManagedClient` daemon can
fail an initialization check-in and restart after Apple's roughly ten-second
respawn delay. This is not the login-window helper stopped before shutdown.
The default protection remains: removing it amplifies persistent failures,
and the investigated prevention workaround adds a privileged broker and
private APIs. Neither workaround ships. Synthetic queued profile queries
have server-side recovery evidence, not a guarantee of client receipt or all
MDM operations. `docs/decisions/0038` records the decision and limits.

Snow Leopard keeps its native critical-updater shutdown behaviour too. An
active `crsud` ignores TERM while its own work finishes; an early halt can
therefore take longer. The final gate's halt took 15 seconds, including
12.664 seconds after TERM for that updater. Its exact outstanding work was
not isolated, and no disabling or forced-abort workaround ships.

These remain scoped defaults, not universal hardware/session proof. The
broader uptime/removal/GUI and alternative-firmware/hardware comparisons,
real-Mac corroboration and additional per-environment runtime targeting are
explicitly deferred for this release. In particular, the 10.9 helper still
kills ManagedClient unconditionally at shutdown and telemetry quarantine is
OS-scoped. `docs/decisions/0039` records these owner decisions and the
separate accepted historical F10/F12 observations without claiming fixes.

A bare `sudo shutdown` of your own can still stall, by any of these
causes: use `sudo /usr/local/sbin/guest-macosx-shutdown -r` (or `-h`) instead.
`docs/decisions/0019` and `0021` have the measurements.

A restart or shutdown in about a boot's first 12 seconds no longer loses
that boot's log. In our measurements, at 7 to 12 seconds, 11 times in 100
(16 in 100 in an earlier run), the boot's whole `system.log`, and
the same messages in the ASL store (what `syslog` and Console read), were
never written: the log daemon, `syslogd`, asks its helper `aslmanager` to
check the logs as it starts, and waits for the answer before it writes
anything. `aslmanager` starts on demand and quits once it has answered and
done its checks,
and when `syslogd` asked a second time just after it quit, `launchd` held
the relaunch for its usual 10 seconds. A shutdown in those seconds stopped
`syslogd` with everything it had not written. Files other programs wrote
were never affected. The first boot now sets `ThrottleInterval` to 0 in
`aslmanager`'s own `launchd` job, so `launchd` relaunches it at once. This
covers every shutdown, `sudo reboot` included; `guest-macosx-shutdown`'s
wait for jobs still starting already kept its own shutdowns out of those
seconds. `docs/decisions/0031` has the mechanism and the measurements.

The system's event agent, `UserEventAgent`, no longer crashes the way it
did as it started. Sometimes, a second or two into a boot, it did, and 10.9 kept a
crash report that fails the boot gate. Its telemetry plugin, which only
feeds 10.9's power and usage statistics, opened each USB device through a
plugin that the operating system could unload, from another thread, while
that plugin's own code was still running: Apple's bug, not this image's.
The install now moves `com.apple.telemetry.plugin` out of
`/System/Library/UserEventPlugins`, to `UserEventPlugins-disabled` beside
it, and the first boot moves it again after Apple's update puts it back.
`docs/decisions/0020` has the mechanism and the measurements.

The install also sets aside 10.9's three statistics jobs, the telemetry
plugin's consumers: `com.apple.systemstatsd`, `com.apple.systemstats.daily`
and `com.apple.systemstats.analysis` move from `/System/Library/LaunchDaemons`
to `LaunchDaemons-disabled` beside it. At 00:15 guest time (US/Pacific, the
installer's default) the daily job asks the statistics daemon for data,
which the daemon asks the telemetry plugin for. Without the plugin no answer
comes: the daemon stayed busy for the rest of the boot, and every later
shutdown stalled 20 seconds and kept a `.shutdownStall` report (12 of 12
guests up across their first 00:15, in our measurements; none of 12 with
the jobs set aside). The daily job also keeps a `powerstats` diagnostic
report, with the plugin or without it, which the boot gate fails on.
Without the plugin there were no statistics to keep. `docs/decisions/0022`
has the mechanism and the measurements.

Boxes now boot to the login window, not a desktop, and say why. The
first boot asked 10.9 to log the guest account in automatically, but no
build gave the account a password it knew, so every boot's automatic
login failed (36 of 36 base-box boots logged it) and left the login
window anyway. The first boot now turns automatic login on only when the
account has a password the first boot has checked works, and otherwise
turns it off and logs why. Nothing this project runs needs a desktop:
the build, the boot gate and Vagrant all go through SSH. A password
given to the first boot no longer appears in its logs, and Snow Leopard
builds now zero their free space last, as 10.9 builds do, so the blocks
of the first boot's settings file, which held that password, go too.
That adds a few minutes to a Snow Leopard build (reasoned from 10.9's,
not yet measured).

Snow Leopard images now have all of Security Update 2013-004, and no
crash reports from their first boot. The first boot installed 2013-004 on
the same boot as the 10.6.8 combo, before the combo's restart, onto a
system that was half 10.6.0 and half 10.6.8. Every 10.6.8 image built
with `updates = security` kept three crash reports from that boot
(`MRTAgent`, `configd`, and launchd's own `/var/log/launchd-pid1.crash`).
Because launchd crashed, the combo's deferred files went in last, over
2013-004's: those images run the combo's older CoreFoundation (6.6.5, not
6.6.6), Security and Spotlight, though they carry 2013-004's receipt. The
first boot now installs each update on its own boot when the update
needs a restart, and brings the kext caches up to date before each 10.6
restart where they are stale. Without that step, 2 of 3 builds panicked
10.6.0's kernel at the restart after the combo. With both, none of 4
builds kept a crash report or panicked, and all 4 had 2013-004's
CoreFoundation. A build costs one more boot, about a minute. The Snow
Leopard template's checks now fail a build that keeps a first-boot crash
report, or whose CoreFoundation is not 2013-004's. `docs/decisions/0023`
has the mechanism and the measurements.

Snow Leopard boxes no longer come up, now and then, with no SSH at all.
On 10.6.0, about one restart in ten in our measurements reached the login
window with nothing listening on port 22, and stayed that way until the
next restart: every connection was reset, and nothing was logged. The
cause is a race in Apple's 10.6 startup. The system sets up SSH's
listening sockets about a second into the boot, IPv6 first, but the 10.6
kernel turns IPv6 on a little later, from a timer of its own, and when
the IPv6 socket fails the system gives up SSH's IPv4 socket too. A 10.6
image now has an `/etc/rc.server`, which the system runs before it sets
up any socket, that waits for IPv6, a fraction of a second, and logs each
wait to `/private/var/log/guest-macosx-rc.server.log`. With it, none of
93 boots of 10.6.0 lost SSH, against 10 of 92 without. 10.6.8 never lost
SSH in 75 boots, but loses the same race for the printing system's IPv6
socket on every boot, and gets the same wait. Rebuild a Snow Leopard box
to get it. `docs/decisions/0029` has the mechanism and the measurements.

Boxes now start about 30 seconds sooner from a cold start, and every
machine has a host UUID of its own. A fresh QEMU starts with an empty
firmware settings store, and the firmware named no host UUID, the
identifier Mac OS X keys per-machine settings by. So 10.9's preferences
daemon waited 30 seconds for one before giving up, the daemons and drivers
that start after it waited too, and the guest answered SSH about 30
seconds late, at every `vagrant up` and every boot gate run. For that
boot, the system's per-machine settings were kept under an all-zero
identifier. On 10.6 the same gap showed as "unable to determine UUID for
host. Error: 35" from six daemons at every cold start. The firmware now
takes the machine's UUID from whatever runs the box, and everything here
that starts QEMU gives it one of its own: each build, each boot gate run,
and each Vagrant machine, which keeps its UUID, and a network address made
from it, across `vagrant halt`, `up` and `reload` (in
`.vagrant/machines/<name>/qemu/guest-macosx-host-uuid`; a `vagrant
destroy` that goes ahead forgets it, one you decline keeps it, and `vagrant
up` says which UUID and address the machine got). Two boxes no longer share
an identity or a network address.
The screensaver setting the build makes for the account is per machine,
so the box now gives it to its own machine at boot, where that machine
has none. A QEMU you start yourself should pass `-uuid` too: without one
the guest makes its UUID from its network address, late, and 10.9 waits
30 seconds at each cold start. `docs/decisions/0024` has the mechanism and
the measurements.

All seven changes are in what the base image is built from:
- The next build rebuilds the firmware, and the next box you build gets
  all seven fixes.
- A box built before this release keeps its old firmware and its stall
  reports, and has no `guest-macosx-shutdown`, so its `vagrant halt` can still
  stall, its event agent can still crash as it starts, and its cold starts
  still wait 30 seconds. Rebuild it to stop the restart hangs, the stalls,
  the crashes and the wait. Rebuild every
  Snow Leopard 10.6.8 box, too: rebuilding is the only way it gets all
  of 2013-004.
- The base recipe changes, so mavericks-vm builds its cached base image
  and the Aqua Transport layer over it again, once.

One 10.6 build in three on a busy host stopped at the installer's
"Install Failed" sheet ("The Installer encountered an error that caused the
installation to fail"), about two minutes into its install, then waited
out its hour for SSH. The likely cause was this project's own: the script
that prepares the disk left a loop running that copied logs onto that
disk every 5 seconds, and the installer unmounts the disk to check it
before installing onto it. A file of ours held open there, or one written
where the disk was about to be mounted again, was measured to fail the
install the same way; the loop itself, at its own pace, was never caught
doing it (that failed build left no log to say). The loop is gone, and
nothing of ours touches the disk once the installer starts.

A failed Snow Leopard install now says why. Its installer keeps no log
file of its own until it starts copying, and Packer deletes a failed
build's output directory. The build now writes the install's log, as it
is written, to `output-snowleopard-install.log`, beside the output
directory, where a failed build leaves it until the next build starts a
new one. Mavericks builds keep theirs the same way, in
`output-mavericks-install.log`. `docs/decisions/0027` has the mechanism
and the measurements. The installer media changes, so the next build of
each builds its media again, once.

A failed install now ends its build in a minute or two, not after the
hour Packer waits for SSH, and says why. Once the installer says it
failed, the guest answers SSH with a message that says so, which Packer
counts as a refused login; both templates tell Packer to give up after
ten. Packer's error then carries the guest's words: "INSTALL FAILED: ...
Its log is output-snowleopard-install.log" (or Mavericks'), wrapped in
Packer's own "authentication error". `docs/decisions/0028` has how.

A Snow Leopard image's disk is now named "Snow Leopard", not "Mavericks",
as Finder, Disk Utility and `diskutil` show it. A Mavericks image's disk
is still "Mavericks", and what its installer media holds is unchanged.
A Snow Leopard box built before this release keeps a disk named
"Mavericks": rebuild it to rename it.

The boxes' settings have new names, the same for every box and every
provider, and the old names are gone:
- `GUEST_MACOSX_GUI=1 vagrant up --provider qemu` opens a window: `cocoa`
  on macOS, `gtk` elsewhere. It takes `1`, `true` or `yes` for a window,
  and `0`, `false`, `no` or nothing for none; anything else stops the
  command, naming the variable. It replaces `MAVERICKS_DISPLAY`. The box
  also sets VirtualBox's and VMware's own window switch from it, for boxes
  on those providers, which this project does not build yet.
- `GUEST_MACOSX_QEMU_DISPLAY` picks QEMU's display, such as `sdl`, and
  opens it without `GUEST_MACOSX_GUI`.
  `GUEST_MACOSX_QEMU_DISPLAY=vnc=127.0.0.1:1` shows a guest on a host with
  no screen of its own, over VNC on the host's port 5901. `none` means no
  display, as leaving it unset does.
- `GUEST_MACOSX_CPU_ISA` replaces `MAVERICKS_CPU_ISA`, with the same
  `none`, `avx` and `avx2`. A Snow Leopard box has no measured levels: it
  says it ignores the variable, and boots as it was built.

Without Vagrant, a build shows its own screen with `-var headless=false`,
added to the template's own `packer build` line, and each template's new
`display` variable picks QEMU's display for it (`gtk` when left empty). A
`display` on a headless build is refused, naming both. No build has been
run with a window yet.

A box keeps the Vagrantfile it was built with, so a box built before this
release reads only the old names, and so does an Aqua Transport box built
over one. Rebuild it to use the new names.

The names this project gives what it puts in a guest, and in Packer's
cache, no longer name 10.9 or the project, so they suit every release it
builds: they were renamed on 2026-10-17 from `mqg` to `guest-macosx`. A
box now carries `/usr/local/sbin/guest-macosx-shutdown`, keeps its first
boot's log at `/private/var/log/guest-macosx-firstboot.log` and its first
boot's settings under `/private/var/db/.guest-macosx-firstboot`, and runs
that first boot from `/Library/LaunchDaemons/guest-macosx.firstboot.plist`
(label `guest-macosx.firstboot`), installed by `guest-macosx-firstboot.pkg`.
A box built before this release keeps the old names
(`/private/var/log/mqg-firstboot.log`, `/private/var/db/.mqg-firstboot`)
and works as it did; only a rebuild renames them.

The plugin's store moves from `mavericks/` to `guest-macosx/` in Packer's
cache directory, so the first build after upgrading downloads and builds
everything again. A build that sets `cache_dir` itself keeps that
directory, and only builds again. To keep Apple's 5 GB installer and the
other downloads, move `mavericks/cache` to `guest-macosx/cache` before that
build, or, if `guest-macosx/cache` already exists, move what is inside
`mavericks/cache` into it (each file is checked against its pin again as it
is used); then delete the rest of `mavericks/`. The longer name leaves less
room for the firmware build's path: with the default cache directory
(`~/.cache/packer`, when neither `PACKER_CACHE_DIR` nor `XDG_CACHE_HOME` is
set), a home directory longer than 22 bytes, such as
`/home/firstname.lastname`, now needs `PACKER_CACHE_DIR` set to a shorter
path; before, the limit was 25. The firmware build says so before it
fetches anything.

Installer media now builds on a Linux host whose running kernel has no
HFS+ module, when another installed kernel has one and its image is
readable by the user running the build. The media is put
together in a small VM that boots one of the host's kernels and loads
that kernel's `hfsplus` module. It always booted the running kernel, so
on a host whose running kernel had no `hfsplus` (Ubuntu's Azure kernels
through 6.17, without `linux-modules-extra`) the build failed late,
mounting the installer, as if the installer were at fault. The VM now
boots the newest installed kernel that has every module it loads, when
the running one does not, and the build's log says which kernel and why.
With no such kernel, the build stops before it starts the VM, and names
the missing module, when the running kernel lists what it builds in, as
distributions' kernels do; one that does not is booted as before.

Guests now get OpenSSH 10.6p1 (10.6p1-mavericks.3, with LibreSSL 4.4.0)
in place of 10.5p1. It carries upstream's security fixes, among them
compression that no longer leaks across channels. On the command line,
`ssh` now refuses a username containing `$` or `\`.

A `vagrant halt` or restart of a guest nobody had logged into yet took
about 20 s longer than one after a login: the boot's first SSH login
started Apple's `sandboxd`, and the guest's shutdown waited for it as for
any job still starting. The family's OpenSSH now applies its sandbox
without `sandboxd` (`docs/decisions/0033`).

A build's guest no longer reaches the internet. Apple's own background
jobs did, during every build: on 10.9 the first-run Software Update scan,
whose catalog the image kept, the push service's device activation, and
certificate revocation checks; on 10.6.8 the XProtect updater and the
critical-update daemon, which exists to download and install the updates
Apple marks required (in the builds measured, it never got as far as a
catalog). Every template
now gives its guest a network that goes no further than QEMU, so the image
holds nothing they fetched. Builds take about as long as before, though
10.9's first-boot install of Security Update 2016-004 takes about three
minutes longer, checking certificates it cannot fetch. The Aqua Transport
build no longer fetches anything itself, so it no longer shows that the
box's `curl` reaches github.com and the rest; the boot gate and
mavericks-vm's self-test show that where the box runs. A box's own
network is unchanged. `docs/decisions/0034` has the measurements.

A Mavericks build now installs an update containing a kernel with `kextd`
held off, checks the final kernel cache, and restarts before enabling SSH.
Previously the update and `kextd` could rebuild caches at the same time;
once in three measured builds, `kextd` held shutdown for 61 seconds while
logging `delaying reboot`. The new sequence keeps the installed kernel and
its cache together and boots them before provisioning can continue. A
failed cache check leaves SSH off and fails the bounded build rather than
publishing an image in that state. Builds without a kernel update do not
use this hold. `docs/decisions/0036` has the applicability and evidence.

Mavericks and Snow Leopard guests now have the same devices, in every
build and box. The firmware's own disk is no longer a USB stick: it is a
disk only the firmware reads, which the guest never sees, and USB carries
only a keyboard and a pointer. So a Snow
Leopard box's window now takes a keyboard and a pointer too; before, it
showed the screen and took no input, because the USB controller its
keyboard would have needed hung Snow Leopard's installer. The pointer on
both releases is a USB tablet, so the window needs no grab, but it lands
about 1.18 times as far from the centre of the screen as the host's
pointer: that is Apple's HID driver, which trims 15% off each axis of an
absolute pointer. Keyboard Setup Assistant no longer asks about QEMU's
keyboard, over Snow Leopard's login window or in a Mavericks desktop. In
our measurements, 150 restarts and 30 cold starts of a Mavericks box, and
the same of a Snow Leopard box, all came back, with the keyboard and the
pointer working each time. A box built before this release keeps its own
Vagrantfile, so nothing changes for it: a Snow Leopard window still takes
no input, and a Mavericks desktop still shows Keyboard Setup Assistant.
To get the new devices, rebuild the box and add it again with `vagrant
box add --force`. Build an Aqua Transport layer only over a base box
built with this release: the layer's box keeps its base box's
Vagrantfile, so a layer over an older base would carry the old devices,
and the layer's build now refuses such a base, naming it.
`docs/decisions/0035` has the measurements.

The boot gate, which checks a change to this project by building and
booting a box from it, now checks Snow Leopard too. Before, it built and
booted Mavericks alone, so a change to the firmware and boot stack both
releases share was checked on one of them. Now `bin/gate.sh --installer
<your disc image>` gates Mavericks and then Snow Leopard, and passes only
when both pass; without a disc it refuses, rather than skip Snow Leopard,
and `--release 10.9` or `--release 10.6` gates one release on purpose. A
Snow Leopard run does every check a Mavericks run does but the two that
need the Aqua Transport layer, which Snow Leopard does not have yet; it
marks those not applicable and says why. The gate now also fails a guest
that has `/var/log/launchd-pid1.crash`, the file Snow Leopard's launchd
writes when it crashes itself. It checks a Mavericks guest for the file
too, but does not expect to find one there: by our reading of
Mavericks' launchd source, which we have not tested, its launchd no
longer writes that file, so on Mavericks this check would not catch a
launchd crash. `docs/decisions/0014` has the details.

A box's Vagrantfile now names its release on a comment line of its own,
which Vagrant ignores, so the gate can tell the two apart from the box
itself. If you drive `bin/gate-vm.sh` by hand, it refuses a box built
before this release, which has no such line, and names the file: rebuild
the box. `bin/gate.sh` builds its own boxes, so it is not affected.

Snow Leopard's update chain now stops if a predecessor package is missing,
its installer fails, or its existing timeout expires; verification rejects
that failure even if a receipt is present. It never installs a dependent
update onto that unsuccessfully updated base or retries the failed one.
Successful updates keep their existing restart policy and timeout bounds.

Host-side safety checks now reject cache paths that cleanup could delete
outside its owned directory, preserve firmware patch provenance across an
interrupted rebuild, and verify a QEMU process's unique run identity before
signaling a recorded PID. Cleanup confirms exit within its existing budget;
a stale PID cannot be trusted merely because another QEMU now has it.
The flash-write gate also drains QEMU's trace-help output so a pipe failure
cannot silently select its timing fallback instead of checking write counts.

Development builds now report a development version, rather than looking
like the last published release. A published plugin still reports its tagged
version; scripts should not treat a development build as that release.

Known networking issue: vagrant-qemu binds forwarded SSH ports on every host
interface, not only loopback. Until that provider behavior is fixed, use a
host firewall or a trusted network; do not assume the forwarded port is
private to the host. The boot gate's own forwards bind to loopback, but that
does not change Vagrant's behavior. This release does not fix the provider.

The image, and any box made from it, contain Apple's operating system. Never
publish either one.
